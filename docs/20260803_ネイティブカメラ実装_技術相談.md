# 技術相談: Ingenic T31 で libimp を使う自前プログラムが初期化で止まる

作成日: 2026-08-03
相談者: nerves_system_atomcam2 開発者

## 相談の要点

Atom Cam 2(Ingenic T31)で、ベンダー製カメラアプリ(`iCamera_app`)に依存せず
libimp を直接使う映像パイプラインを作ろうとしている。その第一歩として
Ingenic 公式サンプル `sample-Encoder-h264` をクロスビルドして実機で動かしたが、
**プロセスは生きているのに初期化が進まず、CPU を回したまま何も出力しない**。

float ABI の不一致は特定・解消済み。次の一手について助言をいただきたい。

## 1. 背景: なぜ自前実装か

現在はベンダーアプリのエンコード出力を `LD_PRELOAD` フックで横取りし、
v4l2loopback 経由で RTSP 配信している。実機では動作しているが、
ベンダーアプリがブラックボックスであるため次の問題を制御できない。

- モバイルアプリが HD ライブに切り替えるとエンコーダチャンネルが競合し、
  RTSP のフレーム供給が止まる
- HD/SD 切り替えを繰り返すとベンダーのエンコーダパイプライン全体が停止し、
  **自動復旧しない**(要電源再投入)
- 解像度・fps・ビットレートを一切変更できない

映像パイプラインを自前で持てば、いずれも解決する。

## 2. 環境

| 項目 | 値 |
| --- | --- |
| SoC | Ingenic T31(MIPS32、リトルエンディアン、シングルコア) |
| RAM | Linux に 92MB 割り当て(`MemTotal` 87,700 kB)。スワップなし |
| カーネル | Linux 3.10.14(`3.10.14__isvp_swan_1.0__`、ベンダー提供バイナリ) |
| ユーザー空間 | Nerves(Buildroot + Erlang/OTP、**musl、soft-float**) |
| センサー | GC2053(`sensor_gc2053_t31` モジュール) |

**実機に存在するベンダー資産**(すべてデバイス上、再配布はしない):

- カーネルモジュール `/atom/system/driver/`: `tx-isp-t31.ko`(770KB)、
  `sensor_gc2053_t31.ko`、`avpu.ko`、`audio.ko` ほか
- ユーザー空間ライブラリ `/atom/system/lib/`: `libimp.so`(986KB)、
  `libalog.so`、`libsysutils.so`
- ISP チューニング `/atom/system/etc/sensor/`: `gc2053-t31.bin`、
  `gc2053-t31-cust.bin`

## 3. これまでの経過

### 試行 1: musl + uclibc 版 libimp → `Bus error`

本システムのツールチェーン(musl)でビルドし、
[gtxaspec/ingenic-lib](https://github.com/gtxaspec/ingenic-lib) の
T31/1.1.1/uclibc/5.4.0 の静的ライブラリをリンク。実行すると即座に
`Bus error`(SIGBUS、rc=138)。

ELF 属性を照合して原因が判明した。

| 対象 | FP ABI |
| --- | --- |
| ベンダー `libimp.so` | **Hard float(倍精度)** |
| 本システムの musl sysroot(`crt1.o`) | **Soft float** |

本システムの musl は soft-float でビルドされており、hard-float の libimp と
同一プロセスに同居できない。

### 試行 2: glibc(hard-float)版 → クラッシュは解消、しかし初期化が進まない

[Bootlin](https://toolchains.bootlin.com/) の
`mips32el--glibc--stable-2025.08-1`(GCC 14.3.0、**hard-float**)を入手し、
ingenic-lib の **T31/1.1.1/glibc/5.4.0** の静的ライブラリとリンクして
静的バイナリ(1.87MB)を生成。ELF 属性は
`FP ABI: Hard float (double precision)` で libimp と一致。

実機での実行結果:

- **`Bus error` は解消。プロセスは生存する**
- しかし `State: R (running)` のまま**数分経っても何も起きない**
- **`VmRSS: 420 kB`** — 1.87MB の静的バイナリとしては小さすぎ、
  初期化がほとんど進んでいないことを示唆
- **`Threads: 1`** — libimp が動いていればワーカースレッドが複数あるはず
- 標準出力のログはゼロバイト(ただし stdio がフルバッファリングのため、
  出力が無いことの証拠にはならない)
- 出力ファイル `/tmp/stream-*.h264` は生成されない

つまり **`IMP_System_Init()` 付近で無限ループに入っている**と見ている。

### 実行時の前提条件はすべて満たしていた

- ベンダープロセス(`iCamera_app`、`assis`、`hl_client`)は 1 つも動いていない
- カメラモジュールを手動 insmod 済み:
  `tx_isp_t31`、`sensor_gc2053_t31`、`avpu` が Live
- デバイスノード生成済み: `/dev/tx-isp`、`/dev/isp-m0`、`/dev/avpu`、
  `/dev/framechan0-2`
- 空きメモリ 8〜20MB(この機体としては潤沢)

### ビルド時に当てたシム

- `IMP_ISP_Tuning_SetWDRAttr` が SDK 1.1.1 に存在しないためスタブ化
  (サンプルは WDR 無効化にしか使わない)
- サンプルに GC2053 の定義が無いため追加(I2C アドレス **`0x37`** と推定、
  1920×1080)

## 4. 直前に気づいた重大な差異(未検証)

質問書作成中に、**リンクしたライブラリと実機のライブラリでビルド系が
異なる**ことに気づいた。

| 対象 | libc | コンパイラ |
| --- | --- | --- |
| **実機の `libimp.so`** | **uclibc**(`NEEDED: libc.so.0`) | **GCC 4.7.2**(Ingenic r2.3.3 2016.12) |
| 試行 2 でリンクしたもの | glibc | GCC 5.4.0(Ingenic r3.3.0-gcc540 2018.04) |

同じ「1.1.1」でも**ビルド系統が違う別物**だった可能性がある。

さらに ingenic-lib には
**T31/1.1.1/uclibc/4.7.2**(GCC 4.7.2、実機と完全一致)も存在することを
確認した。まだ試していない。

## 5. 質問したいこと

1. **`IMP_System_Init` 付近で無限スピンする典型的な原因は何か。**
   `VmRSS` 420KB・単一スレッドで `State: R` を維持する挙動から、
   何を疑うべきか(ISP の初期化順序、デバイスの ioctl 待ち、
   チューニングデータの未ロード、など)

2. **libimp とカーネルモジュールの版数整合はどこまで厳密か。**
   実機の `.ko` と、ingenic-lib の別ビルドの libimp を組み合わせるのは
   そもそも成立するのか。**実機の `libimp.so` を直接動的リンクする**のが
   正解か(静的リンクにこだわる理由は Nerves の musl 環境で動かすためだが、
   uclibc 依存の `.so` を使うなら結局 uclibc 環境が必要になる)

3. **ベンダー独自の前処理が必要か。**
   ベンダーは `ver-comp` という実行ファイルを起動時に走らせている。
   ISP やセンサーの初期化にベンダー固有の手順(センサー電源、リセット GPIO、
   I2C 設定、チューニングデータのロード)が必要で、モジュールの insmod だけ
   では不足している可能性はあるか

4. **GC2053 の I2C アドレスは `0x37` で正しいか。**
   推定で設定したが、誤っているとセンサー検出で無限に待つ可能性がある。
   T31 + GC2053 の一般的な値を知りたい

5. **thingino/prudynt-t を移植する場合の勘所。**
   最終的には [prudynt-t](https://github.com/gtxaspec/prudynt-t) の移植を
   考えている。thingino は同じ T31 + GC2053 の構成(Wyze Cam v3)を
   サポートしており、本システムの制御カーネルも Wyze Cam v3 の GPL ソースから
   ビルドしている。**thingino のセンサー設定・初期化手順をそのまま流用できるか**、
   注意点があれば知りたい

6. **soft-float の musl 環境と hard-float の libimp を共存させる現実的な方法は
   あるか。** 現状は「静的リンクした hard-float バイナリを別プロセスとして
   起動する」ことを想定している(プロセスが分かれていれば ABI 差は問題に
   ならないはず)が、この理解で正しいか。他に注意点はあるか

## 6. 補足

- **musl sysroot 全体を hard-float で再ビルドする案**もあるが、
  Erlang/OTP を含む全パッケージに波及するため、現時点では採らない
- ベンダーアプリと自前実装は **ISP を専有するため排他**であり、
  自前モードでは Atom モバイルアプリが使えなくなることは織り込み済み
- 参考にしている先行実装:
  [mnakada/atomcam_tools](https://github.com/mnakada/atomcam_tools)
  (同一ハードで libimp 直叩きの実績。ただし **glibc** ビルドで
  ベンダーファーム上で動作しており、本件のように別ユーザー空間へ
  統合してはいない)
