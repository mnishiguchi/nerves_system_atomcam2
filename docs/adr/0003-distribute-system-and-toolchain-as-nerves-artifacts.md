# ADR 0003: Distribute the system and toolchain as Nerves artifacts

## Status

Proposed

## Context

A standard Nerves application normally downloads prebuilt system and toolchain
artifacts during `mix deps.get`.

The Atom Cam 2 system and toolchain currently live in this repository and can be
built locally. The example application already attempts to resolve a released
system artifact, but falls back to a local build when the expected GitHub
Release asset is unavailable.

That fallback is useful while developing the system, but it is not an adequate
default workflow for application developers:

- A fresh application build depends on a local system checkout.
- The developer must provide a locally prepared cross-toolchain.
- Buildroot is invoked even when the system has not changed.
- Clean-room and continuous-integration builds are difficult to reproduce.
- The repository cannot yet be consumed like a normal custom Nerves target.

The system and toolchain projects are currently co-located and use coordinated
versions.

## Decision

Publish versioned prebuilt artifacts for both the Atom Cam 2 toolchain and the
Atom Cam 2 system through GitHub Releases.

Use the standard Nerves artifact workflow:

- Build artifacts with `mix nerves.artifact`.
- Declare the GitHub repository in each package's `artifact_sites`.
- Name release tags using the standard `v<version>` convention.
- Upload the exact artifact filenames generated by Nerves.
- Treat a release as incomplete when either the toolchain or system artifact is
  missing.

Keep the system and toolchain package versions synchronized while both packages
are released from this repository. If their release cycles need to diverge,
separate release ownership or explicit artifact tag mapping must be decided
before changing the version relationship.

Add an automated release workflow that:

1. Runs repository validation.
2. Builds the toolchain artifact.
3. Builds the system artifact with the intended toolchain.
4. Verifies artifact names and checksums.
5. Creates or updates the matching GitHub Release.
6. Uploads both artifacts.
7. Performs a clean-room download and firmware build before the release is
   considered complete.

The example application must use released artifacts by default.

Local source development remains supported only through explicit overrides such
as `NERVES_SYSTEM`, `NERVES_TOOLCHAIN`, or the existing project-specific source
override. These overrides must not be required for an ordinary application
build.

A clean-room verification must start without:

- A local checkout override
- A manually selected toolchain
- A previously cached Atom Cam 2 artifact
- A pre-existing Buildroot output directory

The verification application may be the repository example initially, but the
acceptance test must also prove that an independently generated Nerves
application can consume the target dependency.

## Consequences

### Positive

- `mix deps.get` can retrieve the system and toolchain like other Nerves
  targets.
- Application builds avoid unnecessary Buildroot and toolchain work.
- Continuous-integration and onboarding workflows become reproducible.
- Artifact checksums continue to protect the relationship between package
  source and the downloaded archive.
- The local system-development workflow remains available when explicitly
  requested.

### Negative

- Releases must contain two large generated assets.
- Toolchain and system version coordination becomes part of the release
  process.
- Release automation must run on infrastructure capable of building the
  toolchain and system.
- A source change covered by the Nerves checksum invalidates the previous
  artifact and requires a new release.

## Implementation constraints

- Do not commit generated artifact archives to the repository.
- Do not silently fall back to a local checkout in clean-room verification.
- Do not publish a release whose artifacts were built from uncommitted source.
- Preserve the existing protected-kernel verification during the system build.
- Keep development overrides explicit and documented.
- Avoid publishing application secrets or local environment configuration in
  workflow logs or release assets.

## Acceptance criteria

- A version tag produces both expected artifacts.
- The GitHub Release contains both exact Nerves-generated filenames.
- A fresh cache downloads the toolchain and system without a 404.
- `mix deps.get` does not invoke a local system build.
- `mix compile` and `mix firmware` succeed without local target overrides.
- The resulting firmware boots on the Atom Cam 2.
- The example application's documented default workflow uses released
  artifacts.
- A separate clean-room Nerves application can target Atom Cam 2 with only the
  declared dependency and target configuration.
