## 1. RTSP 実装方針の決定

RTSP 配信に 3 方式が並存する状態になったため、期待値
(成功確率 × 価値 ÷ 工数)で評価し、方針を決めた。

| 方式 | 内容 | 位置づけ |
| --- | --- | --- |
| A | ベンダーアプリの出力を LD_PRELOAD で横取り(現行) | 製品路線 |
| C | 方式 A のまま監視層を強化 | **最優先開発** |
| B | libimp を直接叩く自前実装 | 研究テーマ |

**方式 A+C を「暫定版」ではなく完成形とみなす。** 無人運用の IP カメラで
重要なのは「リブートが起きないこと」ではなく「人手なしで復帰できること」。
市販の NAS・ルーター・監視カメラも「内部異常 → 自動再起動」で復帰する設計は
一般的で、ウォッチドッグ復帰の方がむしろ信頼性が高い。

方式 B は成功すれば価値が大きい(ブラックボックス排除、`iCamera_app` の
RSS 18MB 削減、解像度・fps の自由)が、停止箇所が `IMP_System_Init`
(カーネル/ISP 境界)で成否・工数が読めず、期待値が低い。

## 2. フレーム心拍による停止の可視化(方式 C 第一段階)

### 動機

[長時間動作 記録](20260802_長時間動作_記録.md)のインシデント B で判明した
「プロセスは running のままフレームだけが枯れる」停止を、監視層が検知できる
ようにする。ループバックにフレームカウンタが無く、ベンダーが running と
偽るこの環境では、フレーム供給の健全性を測る独自の手段が要る。

### 実装

- **video-hook**: 転送フレームごとに心拍ファイル
  (chroot 内 `/tmp/atomcam2-video-hook.beat`)を更新。供給が止まれば
  mtime が凍る
- **RtspServer**: 稼働中に心拍の mtime を監視し、停止が続けば `status` と
  警告ログで可視化(既定で約 1 分後)。テスト 3 件追加(全 52 件通過)

### 重要な設計判断: 素朴な 3 段階復旧は誤り

実装中に、想定していた「RTSP 再起動 → ベンダー再起動 → reboot」が
このシステムでは正しくないと判明した。

- **RTSP 再起動は無効**。停止原因はフレーム供給元(ベンダーのエンコーダ)の
  上流にあり、v4l2rtspserver を再起動してもフレームの来ないループバックに
  繋ぎ直すだけ
- **ベンダー再起動も無効**。ベンダーランタイムは停止後の再開にリブートが
  必要という制約を持つ
- したがって供給停止への実効的な復旧は **reboot のみ**

さらに **reboot はモバイルアプリの正当な HD 視聴と衝突する**。HD ライブ視聴中は
ch0 のフレームが RTSP 側に来なくなる(競合)が、これは異常ではなく、アプリを
閉じれば復旧する。フレーム不在だけを見て reboot すると、視聴中のユーザーを
巻き込む。「回復不能な停止」と「正当な HD 視聴」を安全に区別するには
loadavg など二次シグナルが要る。実機検証を経てから入れるべきなので、
**自動 reboot は後工程に分離**し、まず可視化までを入れた。

### 実機検証で見つけた 2 つのバグ(ユニットテストでは出ない)

心拍はユニットテストでは `frame_health` をモックするため通るが、実機では
心拍ファイルが生成されなかった。「フレームは流れているのに心拍が無い」
(VLC で 739KB 受信・ループバックのフォーマット設定済み・`PollingStream`
失敗ゼロ)という観測から、次の 2 点を特定・修正した。

1. **MIPS の `open()` フラグ値が汎用と違う**。`O_CREAT` を汎用値 `0100`
   (0x40)で定義していたが、**MIPS は `O_CREAT = 0x100`**。誤った値では
   新規作成にならず `ENOENT` で失敗していた
2. **chroot のパス不一致**。フックはベンダー chroot 内で動くため、その `/tmp` は
   Nerves から見て `/atom/tmp`。RtspServer の読み取りパスをそちらに合わせた

修正後、実機で心拍の mtime が前進すること(`…855 → …862`)、RtspServer が
`stall_strikes: 0` で認識することを確認した。

## 3. ネイティブ実装(方式 B)の調査

### 到達点

Ingenic 公式サンプル `sample-Encoder-h264` をクロスビルドして実機で動かした。

- **float ABI 不一致を解消**。本システムの musl は soft-float、libimp は
  hard-float。同一プロセスに同居できず `Bus error` になっていた。Bootlin の
  hard-float glibc ツールチェーンでビルドし直して解消
- ただし **`IMP_System_Init` 付近で初期化が進まず停止**する
  (RSS 420KB・単一スレッド・CPU 100%)

### 判明した最有力原因

質問書作成中に、**リンクしたライブラリと実機のライブラリでビルド系統が
異なる**ことに気づいた。

| 対象 | libc | コンパイラ |
| --- | --- | --- |
| 実機の `libimp.so` | uClibc 0.9.33.2 | GCC 4.7.2 |
| 試したもの | glibc | GCC 5.4.0 |

Ingenic 系 SDK は OEM ごとに libimp・tx-isp・センサドライバが改変されており、
SDK 番号(1.1.1)が同じでも互換とは限らない。セカンドオピニオンの助言も
「実機の libimp.so をそのまま使え」で一致。実機の uClibc ランタイムは
`/atom/lib/` に一式存在することを確認済み。

### 副次的な発見

- 実機にセンサー `sensor_gc2053_t31`、ISP `tx_isp_t31`、エンコーダ `avpu`、
  libimp 3 点セット、ISP チューニング `gc2053-t31*.bin` がすべて存在。
  スクラッチ実装の部品は揃っている
- ベンダーに live555 ベースの RTSP サーバー `/atom/system/bin/rtsp`(51KB)が
  同梱されているが、libimp を直接使わず `iCamera_app` からフレームを受ける
  構成のため、ベンダー依存は消えず今回の目的には使えない
- GC2053 の I2C アドレスは `0x37`(Wyze v3 / thingino / OpenIPC と一致)

### 位置づけ

方針決定に従い研究テーマとして保留。実機の libimp.so を使う uclibc ビルドが
次の一手だが、方式決定を優先してツールチェーン取得は保留した。

## 4. 監視設計の参考(hello_usbcam_rtsp)

動作実績のある別プロジェクト
[hello_usbcam_rtsp](https://github.com/kurokouji)(NanoPi NEO + USB カメラ +
Nerves、H264 約 30fps 配信を実機確認済み)の監視設計を調査した。同じ
「Elixir は薄い監視層、配信は v4l2rtspserver」構成で、本システムより優れた点が
ある(`MuonTrap.Daemon` + `trap_exit` による daemon 死の即時検知、ヘルス
チェックによるノード掴み直し)。

ただし本システムでは `MuonTrap` の port helper が保護カーネル(3.10)上で
`:epipe` で落ちる実測があるため、そのままは使えない。設計思想は `Port.open`
で再現でき、方式 C の心拍監視はその第一歩にあたる。

## 5. 得られた知見(再発防止)

- **MIPS の `open()` フラグは汎用値と違う**。freestanding コードで
  `O_CREAT`/`O_TRUNC` 等を自前定義するときは MIPS 値(`O_CREAT=0x100`、
  `O_TRUNC=0x200`)を使う
- **chroot 内で動くフックのファイル出力は、Nerves 側からは `/atom/` 配下に
  見える**。フックとアプリでパスの視点が違う
- **ユニットテストが緑でも実機で動くとは限らない**。心拍は 52 件のテストが
  通っていたが、モックが実機の 2 バグを隠していた。フレーム経路のような
  外部依存は実機検証が要る
- **Ingenic SDK は SDK 番号が同じでも OEM 改変で別物**。libimp の差し替えは
  バージョン文字列だけで判断しない
- **素朴な段階的復旧が常に正しいとは限らない**。復旧手段が実効性を持つか
  (再起動で本当に直るか)を、失敗モードの構造から検証する
