## 1. RTSP 実装方針の決定

RTSP 配信に 3 方式が並存する状態になったため、期待値
(成功確率 × 価値 ÷ 工数)で評価し、方針を決めた。

| 方式 | 内容 | 位置づけ |
| --- | --- | --- |
| A | ベンダーアプリの出力を LD_PRELOAD で横取り(現行) | 製品路線 |
| C | 方式 A のまま監視層を強化 | **最優先開発** |
| B | libimp を直接叩く自前実装 | 研究テーマ |

**方式 A+C を「暫定版」ではなく完成形とみなす。** 無人運用の IP カメラで
重要なのは「リブートが起きないこと」ではなく「人手なしで復帰できること」。
市販の NAS・ルーター・監視カメラも「内部異常 → 自動再起動」で復帰する設計は
一般的で、ウォッチドッグ復帰の方がむしろ信頼性が高い。

方式 B は成功すれば価値が大きい(ブラックボックス排除、`iCamera_app` の
RSS 18MB 削減、解像度・fps の自由)が、停止箇所が `IMP_System_Init`
(カーネル/ISP 境界)で成否・工数が読めず、期待値が低い。

## 2. フレーム心拍による停止の可視化(方式 C 第一段階)

### 動機

[長時間動作 記録](20260802_長時間動作_記録.md)のインシデント B で判明した
「プロセスは running のままフレームだけが枯れる」停止を、監視層が検知できる
ようにする。ループバックにフレームカウンタが無く、ベンダーが running と
偽るこの環境では、フレーム供給の健全性を測る独自の手段が要る。

### 実装

- **video-hook**: 転送フレームごとに心拍ファイル
  (chroot 内 `/tmp/atomcam2-video-hook.beat`)を更新。供給が止まれば
  mtime が凍る
- **RtspServer**: 稼働中に心拍の mtime を監視し、停止が続けば `status` と
  警告ログで可視化(既定で約 1 分後)。テスト 3 件追加(全 52 件通過)

### 重要な設計判断: 素朴な 3 段階復旧は誤り

実装中に、想定していた「RTSP 再起動 → ベンダー再起動 → reboot」が
このシステムでは正しくないと判明した。

- **RTSP 再起動は無効**。停止原因はフレーム供給元(ベンダーのエンコーダ)の
  上流にあり、v4l2rtspserver を再起動してもフレームの来ないループバックに
  繋ぎ直すだけ
- **ベンダー再起動も無効**。ベンダーランタイムは停止後の再開にリブートが
  必要という制約を持つ
- したがって供給停止への実効的な復旧は **reboot のみ**

さらに **reboot はモバイルアプリの正当な HD 視聴と衝突する**。HD ライブ視聴中は
ch0 のフレームが RTSP 側に来なくなる(競合)が、これは異常ではなく、アプリを
閉じれば復旧する。フレーム不在だけを見て reboot すると、視聴中のユーザーを
巻き込む。「回復不能な停止」と「正当な HD 視聴」を安全に区別するには
loadavg など二次シグナルが要る。実機検証を経てから入れるべきなので、
**自動 reboot は後工程に分離**し、まず可視化までを入れた。

### 実機検証で見つけた 2 つのバグ(ユニットテストでは出ない)

心拍はユニットテストでは `frame_health` をモックするため通るが、実機では
心拍ファイルが生成されなかった。「フレームは流れているのに心拍が無い」
(VLC で 739KB 受信・ループバックのフォーマット設定済み・`PollingStream`
失敗ゼロ)という観測から、次の 2 点を特定・修正した。

1. **MIPS の `open()` フラグ値が汎用と違う**。`O_CREAT` を汎用値 `0100`
   (0x40)で定義していたが、**MIPS は `O_CREAT = 0x100`**。誤った値では
   新規作成にならず `ENOENT` で失敗していた
2. **chroot のパス不一致**。フックはベンダー chroot 内で動くため、その `/tmp` は
   Nerves から見て `/atom/tmp`。RtspServer の読み取りパスをそちらに合わせた

修正後、実機で心拍の mtime が前進すること(`…855 → …862`)、RtspServer が
`stall_strikes: 0` で認識することを確認した。

## 3. ネイティブ実装(方式 B)の調査

### 到達点

Ingenic 公式サンプル `sample-Encoder-h264` をクロスビルドして実機で動かした。

- **float ABI 不一致を解消**。本システムの musl は soft-float、libimp は
  hard-float。同一プロセスに同居できず `Bus error` になっていた。Bootlin の
  hard-float glibc ツールチェーンでビルドし直して解消
- ただし **`IMP_System_Init` 付近で初期化が進まず停止**する
  (RSS 420KB・単一スレッド・CPU 100%)

### 判明した最有力原因

質問書作成中に、**リンクしたライブラリと実機のライブラリでビルド系統が
異なる**ことに気づいた。

| 対象 | libc | コンパイラ |
| --- | --- | --- |
| 実機の `libimp.so` | uClibc 0.9.33.2 | GCC 4.7.2 |
| 試したもの | glibc | GCC 5.4.0 |

Ingenic 系 SDK は OEM ごとに libimp・tx-isp・センサドライバが改変されており、
SDK 番号(1.1.1)が同じでも互換とは限らない。セカンドオピニオンの助言も
「実機の libimp.so をそのまま使え」で一致。実機の uClibc ランタイムは
`/atom/lib/` に一式存在することを確認済み。

### 副次的な発見

- 実機にセンサー `sensor_gc2053_t31`、ISP `tx_isp_t31`、エンコーダ `avpu`、
  libimp 3 点セット、ISP チューニング `gc2053-t31*.bin` がすべて存在。
  スクラッチ実装の部品は揃っている
- ベンダーに live555 ベースの RTSP サーバー `/atom/system/bin/rtsp`(51KB)が
  同梱されているが、libimp を直接使わず `iCamera_app` からフレームを受ける
  構成のため、ベンダー依存は消えず今回の目的には使えない
- GC2053 の I2C アドレスは `0x37`(Wyze v3 / thingino / OpenIPC と一致)

### 位置づけ

方針決定に従い研究テーマとして保留。実機の libimp.so を使う uclibc ビルドが
次の一手だが、方式決定を優先してツールチェーン取得は保留した。

## 5. 得られた知見(再発防止)

- **MIPS の `open()` フラグは汎用値と違う**。freestanding コードで
  `O_CREAT`/`O_TRUNC` 等を自前定義するときは MIPS 値(`O_CREAT=0x100`、
  `O_TRUNC=0x200`)を使う
- **chroot 内で動くフックのファイル出力は、Nerves 側からは `/atom/` 配下に
  見える**。フックとアプリでパスの視点が違う
- **ユニットテストが緑でも実機で動くとは限らない**。心拍は 52 件のテストが
  通っていたが、モックが実機の 2 バグを隠していた。フレーム経路のような
  外部依存は実機検証が要る
- **Ingenic SDK は SDK 番号が同じでも OEM 改変で別物**。libimp の差し替えは
  バージョン文字列だけで判断しない
- **素朴な段階的復旧が常に正しいとは限らない**。復旧手段が実効性を持つか
  (再起動で本当に直るか)を、失敗モードの構造から検証する

## 6.5 有線のみ構成でベンダーカメラが起動しない問題(追記)

最新ファームを新品 SD に書き込んで有線 LAN(192.168.1.77)で起動したところ、
RTSP が自動起動しなかった。原因は **ベンダーカメラ連携が wlan0 前提のまま**
だったこと。有線 LAN 対応を追加した際の取りこぼし。

3 箇所が wlan0 に固定されていた。

1. `VendorCamera` の readiness が `["interface", "wlan0", "connection"]` を見て
   いた → wlan0 が `:disconnected` だと永久に `internet_connection` 待ち
2. `atomcam2-vendor-camera` の起動処理が wlan0 の IPv4 アドレスを必須にして
   いた(ベンダーの network-status 報告用にファイルへ書く)→ 有線のみだと
   `wlan0 has no usable IPv4 address` で失敗
3. `TimeSync` も同じ wlan0 依存で、有線のみだと時刻同期が走らない

### 恒久対策

- readiness と TimeSync の接続プロパティを `["connection"]`(全インターフェース
  横断の総合接続状態)に変更。VintageNet はこれを公開しており、実機で
  `:internet` を返すことを確認済み
- `atomcam2-vendor-camera` の IPv4 取得を wlan0 → eth0 のフォールバックに
- precheck のインターフェース健全性チェックを eth0(operstate=up)でも通るように

### 実機検証

恒久対策を入れたファーム(`era-fossil`)を配信し、有線のみのカメラ
(192.168.1.77、wlan0 は `:disconnected`)を再起動したところ、
**ダミー IP 無しでベンダーカメラと RTSP が自動起動**した。
`wlan0` の IPv4 アドレスは 0 件のまま `result=running`、RTSP は
H.264 1080p を配信(VLC で受信確認)、再起動ループもなし(uptime 継続増加)。

### 暫定回避策(恒久対策の投入まで使ったもの)

(旧回避策は恒久対策の投入により不要になった。以下は記録)
リンクの無い wlan0 にダミー IP(`ip addr add`)を割り当てると起動の
wlan0 IPv4 チェックを通せる。wlan0 は未接続なので実通信に影響しない。
ただし再起動で消え、readiness の wlan0 依存は解消しないため手動起動が必要。
恒久対策の投入で不要になる。

## 6.6 複数拠点の Wi-Fi 対応(追記)

単一 SSID を焼き込む作りだったため、カメラを別拠点へ移すと wlan0 が
`:disconnected` になっていた(6.5 の遠因でもある)。**VintageNet は
`networks:` リストで複数ネットワークを持て、電波が届く AP に自動接続する**ため、
provisioning ファイルから複数 SSID を読めるようにするだけで対応できる。

### 実装

- `nerves-provisioning.conf` の形式を後方互換で拡張。番号なしの組が拠点 1、
  `_2`、`_3` … を足して拠点を増やす:

  ```text
  NERVES_WIFI_SSID=home
  NERVES_WIFI_PASSPHRASE=home-secret
  NERVES_WIFI_SSID_2=office
  NERVES_WIFI_PASSPHRASE_2=office-secret
  ```

- 解析は純関数 `Atomcam2NervesApp.WifiProvisioning.networks/1` に切り出し、
  ユニットテスト 7 件(後方互換・オープンネットワーク・番号飛び・順序・
  空白除去)を追加。`runtime.exs` は `MOTDLogo` と同じ流儀でこれを呼ぶ
- **再ビルド不要**。FAT の `nerves-provisioning.conf` を編集して拠点を追加する。
  パスフレーズを空にするとオープンネットワーク扱い

これは system ではなくアプリ(例アプリ)側の変更のため、フルビルドは不要で
`mix upload` だけで配れる。

### 実機検証

2 拠点の設定を投入して再起動したところ、VintageNet の wlan0 設定に
2 ネットワーク(`["aterm-5e6c76-g", "nekonohanami"]`)が反映されることを
確認した(パスフレーズ未所持のため 2 つ目への実接続は未検証だが、
provisioning → runtime.exs → WifiProvisioning → VintageNet の経路が
複数ネットワークを正しく構成することは実機で確認できた)。

### 途中で解決した最大の難所: エンコーダ API の ABI 不一致
- デバイスの libimp は **T31 1.1.1 の新エンコーダ API**。atomcam_tools の
  サンプルヘッダは旧 API(`encAttr`/`rcAttr` 直接指定)で、構造体レイアウトが
  違い `invalid resolution(0x0)` になった。ISP/センサ/FrameSource 系の
  ヘッダは新旧互換だったため Stage 2 は通り、**エンコーダだけ非互換**だった。
- 正しいヘッダを GitHub `cgrrty/Ingenic-SDK-T31-1.1.1-20200508` の
  `include/imp/` から取得し、`IMP_Encoder_SetDefaultParam(...)` +
  `IMP_Encoder_CreateChn` 方式に修正。ストリーム取得は `IMPEncoderPack` が
  絶対アドレスでなく **`offset`** を持つため、`stream.virAddr + pack.offset`
  で読み、リング折り返し(`offset+length > streamSize`)を処理して解決。
- `IMP_ISP_Tuning_SetWDRAttr` はデバイス libimp に存在せず(リンク不可)、
  呼び出しを外した。

### 実機運用で判明した制約
- **`/tmp` は noexec** → バイナリは `/data` から実行。
- 依存 lib は **`/atom/system/lib`**(libimp/libalog/libsysutils)。
  interpreter は `/atom/lib/ld-uClibc.so.0`。
- **`iCamera_app` は stop すると reboot なしに再起動できない**
  (`stopped_reboot_required`)。ISP が空くのは iCamera_app 停止中だけなので、
  停止した窓でスパイクを回し、終了後に `Nerves.Runtime.reboot()` で復旧。
  reboot 後は自動でベンダーカメラ + RTSP が復帰(~100 秒)。各スパイク後に
  実機で VLC 再生の復帰を確認済み。

## 10. メモリ消費の改善状況

方式B の狙いの一つは、ブラックボックスの `iCamera_app` を軽量なネイティブ
プロセスへ置き換えて平常時メモリを削ることにある。今回の実測と見積もりは
[iCamera 非依存 RTSP 配信 提案書](20260803_iCamera非依存RTSP配信_提案書.md)
の「構築内容とメモリ所要量の見積もり」を参照。

### 今回(2026-08-03)実測したベンダーモードの RSS(87MB 側)
`atomcam2-vendor-camera status` と `ps` で確認:

| プロセス | RSS |
| --- | --- |
| `iCamera_app` | 起動直後 17.4MB → 定常 約 22MB |
| `hl_client` | 0.6–1.0MB |
| `assis` | 1.8–2.1MB |
| ベンダー三点計 | **約 25MB** |
| `v4l2rtspserver`(方式A の配信) | 約 13MB |

`memory_reclaimable_kb` は約 26.7MB。フレームバッファは rmem(36MB 予約)側で
プロセス RSS には出ない([[atomcam2-rtsp]] 参照)。

### ネイティブモードの位置づけ
方式B ではベンダー三点(約 25MB)を、ネイティブのエンコーダ常駐プロセスへ
置き換える。提案書の見積もりでは native 常駐は概ね 3–6MB で、配信の後段
(v4l2loopback + v4l2rtspserver、約 13MB)は再利用する。したがって
**平常時 RSS の削減幅は概ね 19–22MB** と見込む。

なお **native 常駐プロセスの RSS 実測は Stage 4(loopback 書き出し)で取得予定**。
本スパイク(短命の一括取得プロセス)では常駐時の実効メモリを代表しないため、
数値は Stage 4 の常駐形態で計測してから確定する。
