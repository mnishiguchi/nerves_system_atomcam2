# 2026-08-03 ダッシュボード 提案書

カメラの状態をブラウザから確認できる Web 画面(ダッシュボード)の提案。
現状の確認手段は SSH(IEx)経由のみで、`VendorCamera.status()` などを
打てる人しか状態を見られない。ブラウザ(PC・スマホ)で一目で確認できる
画面を、本機の厳しいメモリ制約の中で成立する最小構成で追加する。

関連: [平常時メモリ削減 提案書](20260803_平常時メモリ削減_提案書.md)、
[RTSP 配信 提案書](20260802_RTSP配信_提案書.md)、
[長時間動作 記録](20260802_長時間動作_記録.md)

## 背景と目的

- 稼働確認のたびに SSH + IEx が必要で、家族や離れた場所からの
  「動いているか」の確認ができない
- RTSP の映像が止まったとき、原因(camd 停止か、loopback 書き出し停止か、
  サーバ停止か)の切り分けに毎回コマンドを打っている。フレーム心拍や
  各 GenServer の status は既にあるので、見せる場所だけが無い
- 長期運用ではメモリ残量・稼働時間・ファーム状態の推移を気軽に見たい

## 前提と制約(メモリが最優先)

[平常時メモリ削減 提案書](20260803_平常時メモリ削減_提案書.md) のとおり、
本機のメモリ余裕は乏しく、**vendor カメラ(ベンダー三点 約 25MB)は
メモリ容量の問題でもはや起動できない**。運用は方式 B のネイティブモード
(camd 約 1.5MB + v4l2rtspserver 約 13MB)が前提となる。ダッシュボード
自体も同じ制約に従う:

- **Phoenix / LiveView / Plug + Bandit は不採用**。依存追加だけで code が
  数 MB 増え、本末転倒
- **OTP 標準の `:inets` httpd を使う**。`mix.exs` の applications に
  `:inets` は既に入っており(fwup 用)、**新規依存ゼロ・追加コードは
  自前モジュール 1 つ**で済む
- ページは**サーバレンダリングの静的 HTML 1 枚**。JS フレームワーク無し、
  自動更新は `<meta http-equiv="refresh" content="10">` で行う
- 画像・CSS などのアセットは持たない(インライン CSS のみ)

## 表示する情報とデータソース

すべて既存の API / ファイルから読むだけで、新たな計測プロセスは持たない。

運用は方式 B のネイティブモード(camd)が前提。vendor カメラはメモリ
容量の問題で起動できないため、vendor 関連は「起動していないこと」の
確認情報としてのみ扱う。

| 区分 | 項目 | データソース |
| --- | --- | --- |
| カメラ | **native カメラ(camd)の稼働**・PID・RSS | `ps` / `/proc/<pid>/status`、`/data/camd.ctl` |
| カメラ | camd の直近ログ(数行) | `/data/camd.log` の tail |
| カメラ | vendor 残骸の検出(誤って起動していないか) | `VendorCamera.status/0`(参考表示) |
| RTSP | サーバ状態・**フレーム心拍**・stall ストライク | `RtspServer.status/0` |
| RTSP | 接続 URL(`rtsp://<ip>:8554/...`) | `Debug.ip/0` から組み立て |
| NAS | エクスポート状態・最終転送 | `NasExporter.status/0` |
| 時刻 | NTP 同期状態・現在時刻 | `TimeSync` / `NervesTime` |
| ネットワーク | wlan0 / eth0 の IP・SSID・接続状態 | `Debug.wifi/0` `Debug.ip/0` / VintageNet property |
| メモリ | MemFree / MemAvailable / beam RSS | `/proc/meminfo`、`/proc/self/status` |
| ファーム | バージョン・スロット(A/B)・validated | `Nerves.Runtime.KV` |
| 稼働 | uptime・再起動回数 | `/proc/uptime`、`FirmwareHealth` |
| ストレージ | /data・SD の使用量 | `:disksup` は使わず `df` 相当を都度実行 |

## 提案する実装

### Phase 1: 読み取り専用ページ + JSON(本提案の主対象)

`Atomcam2NervesApp.Dashboard` モジュールを 1 つ追加する。

- `:inets` の `:httpd` を supervision tree に追加、**ポート 80**(root 実行
  なので bind 可)
- ルートは 2 つだけ
  - `GET /` — HTML ダッシュボード(10 秒ごと自動リフレッシュ)
  - `GET /status.json` — 同じ内容の JSON(スクリプト・監視からの利用向け)
- レンダリングは EEx をコンパイル時展開(実行時テンプレートエンジン無し)
- 各 status 呼び出しは短いタイムアウト付きで、応答しない GenServer が
  あってもページ全体は返す(該当欄に `unavailable` を出す)

メモリ見積もり: httpd はリスナ + リクエスト毎の短命プロセスのみで、
常駐増は **数百 KB 以下**。code 増も `:inets` ロード済みのため僅少。
実装後に before/after を実測して
[平常時メモリ削減 提案書](20260803_平常時メモリ削減_提案書.md) の
ベースラインへ追記する。

### Phase 2(任意): 操作ボタン

読み取りで運用が回ってから、POST 限定で最小限の操作を足す:

- 再起動(`Nerves.Runtime.reboot/0`、確認ダイアログ付き)
- テスト発声(`atomcam2-aoplay` 呼び出し)

vendor カメラの起動操作は**提供しない**。メモリ容量の問題で起動は不可能
であり、ボタンがあると誤操作でメモリ飽和を誘発するだけのため。

誤操作・いたずら対策として、Phase 2 に入る時点で最低限の認証
(httpd の Basic 認証 or 合言葉トークン)を必須にする。

### Phase 3(研究): 静止画プレビュー

ダッシュボードに現在の映像の静止画を出す案。loopback の H.264 を
デバイス上でデコードする手段が無いため**当面見送り**。代替として
RTSP URL の表示 + VLC で開く手順の記載に留める。

## セキュリティの考え方

- LAN 内限定の読み取り専用ページとして開始(Phase 1 は操作を持たない)
- 表示内容に秘匿情報(パスフレーズ・鍵)は含めない。SSID は表示するが
  パスフレーズは出さない
- 操作(Phase 2)を足す時点で認証を導入。インターネット公開はしない

## リスクと検証項目

| リスク | 検証 |
| --- | --- |
| メモリ増で常用時の余裕をさらに削る | native カメラ(camd)+ RTSP 稼働状態で MemFree / beam RSS を before/after 実測。増分が 1MB を超えるなら設計を見直す |
| status 呼び出しがカメラ動作へ干渉 | 全て既存の読み取り API。ページアクセス連打(10 req/s)でも RTSP 心拍が乱れないことを確認 |
| httpd プロセスの異常でアプリ全体が巻き込まれる | supervision tree で独立 child にし、restart しても他へ影響しないことを確認 |
| ポート 80 が他機能と衝突 | 現状 80 は未使用(RTSP は 8554、SSH は 22)。定数化して変更可能にする |

## 段階的計画

1. Phase 1 実装(Dashboard モジュール + httpd 起動 + HTML/JSON)
2. 実機でメモリ実測・干渉確認 → 問題なければ main へ
3. 運用してみて必要になった操作だけを Phase 2 として追加(認証込み)
